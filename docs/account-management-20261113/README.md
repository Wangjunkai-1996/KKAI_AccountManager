这组文档把五项账号管理需求拆成可独立评审、实现和验收的工程任务。默认运行模式是无人值守：确定性邮箱/手机验证、密码错误和 TOTP 错误会保存原因并停止该账号自动恢复，不等待用户回访，也不会死循环；网络类暂态错误继续按既有退避。新增 P0 规则：Sub2 关联确认不存在后，停止该账号自动检测、恢复和重导入，旧任务与服务重启也不能把它重新创建。

## 实施顺序

1. 后端先落地唯一错误分类来源、Sub2 缺失保护和所有自动入口门禁；本期不增加人工放行字段或新状态机。未来若接入可信验证事件，另立需求并单独设计放行水位。
2. 后端提供单账号单字段凭据 reveal 契约，以及经过身份核对的名称和来源字段。
3. 前端接入规范错误、名称、套餐筛选、Sub2 缺失状态和 reveal 状态；不复制后端分类规则，不把秘密放入列表或普通详情。
4. 按验收计划运行定向测试，先解决 Sub2 缺失/P0 和 L3 阻塞，再验证名称、筛选和窄屏交互。

## 代码质量硬门槛

- 一个错误分类真源；前端只展示规范值。
- 一个恢复队列和现有 lease/CAS；不新造平行状态机。Sub2 缺失保留持久依据，不能通过删除绑定把更新变成新建；首次交付保留。
- 名称只用于展示/搜索；不能替代 destination、绑定 ID、凭据版本或 operation ID。
- reveal 只返回请求字段；普通列表/详情、日志、缓存和错误响应不含明文。
- 迁移只在现有字段确实无法表达本轮创建/更新意图时增加最少字段，并配套默认值、CAS、回滚和旧数据测试。
- 测试报告记录实际命令和行为断言；没有实现的测试只列为缺口。无人值守验收必须证明页面访问、服务重启、定时扫描和人工字段都不能解除确定性阻塞。
